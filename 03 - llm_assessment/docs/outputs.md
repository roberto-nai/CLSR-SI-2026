# Pilot outputs and interpretation

## Current textual-requirement and DECLARE outputs

New requests, result exports and expert dossiers contain the selected textual requirement, exact CSV formula as `declare`, and case evidence, without source quotations or `legal_source` fields. The original `source` column remains in `data/rules_current.csv` and is ignored at runtime. `REQUIREMENT` and `DECLARE` identify the current rule's wording and formula; `CASE`, event and documentary references identify supplied case evidence. Runtime formulation provenance uses `requirement_review_id`.

Future expert sheets use `evidence_support` rather than `source_support`. Non-empty historical source-support ratings require explicit reconciliation; they are not silently converted. Removed source-bearing columns must not return as custom public columns. Existing annotations and private answer-identity guards remain protected. Model names remain visible immediately after `run`, so these forms are not automatically model-blinded.

The current outcomes are compliance, violation and undetermined. A case flag is `yes` for any valid violation, `no` only if every planned answer is valid compliance, and undetermined otherwise. Both phases retain the same textual requirements and formulas. B preserves A's full prompt and adds only fixed document evidence. Neither phase includes quoted legal-source evidence, checker answers or a previous model answer.

Existing outputs retain their original bytes and source-bearing schemas. Their archived executable snapshots are required for verification or reanalysis; current code cannot silently resume or regenerate them. The eleven-case tables and four-outcome descriptions below are historical, not the new export schema.

No live study used the intermediate requirement-only implementation. Existing source-bearing studies and intermediate prompt identities cannot be silently reused under the current requirement-and-DECLARE protocol.

## Current comparison categories

Comparison reports expose Agreement, Disagreement and Undetermined. A valid binary model judgement is compared with the available DECLARE result to determine agreement or disagreement. A legacy non-binary model answer, including `not_applicable`, or an unavailable formal reference yields comparison Undetermined. Technical failures and pending assessments retain their own operational statuses outside these categories.

Use `comparison_category` for the per-row label and `n_comparison_agreements`, `n_comparison_disagreements` and `n_comparison_undetermined` for aggregate counts. Their sum equals the valid-output count. Conditional agreement is Agreement divided by Agreement + Disagreement; an empty denominator remains unavailable. Raw legal outcome fields and independent expert ratings are preserved separately for provenance. The historical output descriptions below retain the original assessment protocol; existing files have not been regenerated by the source-only correction.

The primary `assessment_mode: "case"` pilot writes to `outputs/phase1_2016_2026_1_per_year_32000_20261122`. Eleven cases and three models in phase A produce **33 planned case requests**, each returning 19 rule judgements: **627 planned individual rule rows**. Explicit recovery attempts are additional API calls. All current-cohort requests use a 32,000-token output ceiling. Documentary phase B is deferred; no B API results belong in the active exports. The completed selected dataset contains all 33 valid case responses and 627 valid rule answers, with no technical failure or unavailable judgement in the latest results. One earlier Anthropic formatting failure remains in the attempt audit and resource totals; its valid retry supplies the selected answer.

## Case and rule judgements

`case_results.csv` retains `n_rules`, valid/completed, compliance, violation, not-applicable, uncertainty, pending and failed counts. It links the phase-specific dossier and preserves the rule identifiers and explanations behind a case flag. `case_comparison.csv` presents these case-level results across models/phases without discarding the detailed rule CSV.

The case `violation` flag has this fixed aggregation:

| Value | Rule-level condition |
| --- | --- |
| `yes` | At least one valid answer is `violation`, even if other rule answers remain unresolved. |
| `no` | Every planned answer is valid `compliance` or `not_applicable`. |
| `undetermined` | Neither condition above holds, including substantive uncertainty, pending work or failures. |

The flag describes the tested requirements. It is not a further model response, a formal-checker verdict or a claim that the entire proceedings are legally compliant. The same distinction between unavailable and negative applies to rule-level violation indicators.

`rule_assessments.csv` includes stable `assessment_id`, case/year, phase, provider/model, rule/variant, status, four-label outcome, source, requirement, justification, evidence references and dossier path. `S1` refers to the current row's legal source. CASE and E references identify common case metadata/events. No documentary D passages enter active A answers. Operational errors and invalid or missing answers do not become legal `undetermined` outcomes.

The request unit is a case, but the reported substantive unit is a rule answer. Do not multiply API time, token use or attempt counts by 19 when expanding a response into rule rows. One failed case call can leave 19 rule rows without valid answers. A batch with ambiguous rule allocation invalidates all of them; a complete allocation can preserve independently valid rows despite another row's content error.

## Expert annotations

Each reviewer CSV omits provider/model labels and formal-checker results. Opaque stable IDs align the two experts' rows without revealing the model label. Legal source, requirement, model outcome/justification, evidence references and dossier links remain available. The active dossiers contain exactly the phase-A evidence shared by the models: legal sources, requirements, case metadata and ordered events. Additional case-document text is excluded. Earlier B templates and preparation belong to archived provenance, not the current reviewer package.

Each expert reviews A independently before reconciliation. Any future B evaluation must follow frozen A annotations to limit documentary evidence carry-over. They edit only initially blank annotation fields:

| Field | Allowed interpretation |
| --- | --- |
| `expert_outcome` | `compliance`, `violation`, `not_applicable` or `undetermined` on the supplied evidence |
| `judgement_correct` | `yes`, `no` or `undetermined`; inability to judge correctness is not a negative rating |
| `source_support` | `supported`, `partly_supported`, `unsupported` or `not_assessable` |
| `explanation_quality` | 0–3 using the supplied rubric; leave blank if no answer is assessable |
| `comments` | Rationale, uncertainty and evidence concerns |

No expert labels or scores are filled automatically. An operationally missing response remains unavailable. An expert's substantive `undetermined` outcome is distinct from an unfilled annotation. These are blinded output-review forms, not an automatically independent legal gold standard: the model answer is visible during review.

Reanalysis merges existing ratings and added columns by `assessment_id`. `response_sha256` identifies the displayed response; `annotation_response_sha256` identifies the answer to which annotations applied. `annotation_status=response_changed_since_annotation` flags stale ratings for reconciliation. Do not delete IDs, introduce duplicate IDs or overwrite machine-generated columns. Both expert files are checked before either is regenerated.

## Attempts, resources and formal comparison

The latest recorded attempt determines a case request's exported answers, including when that attempt failed. Earlier attempts remain archived. Interrupted attempts may lack final response records and are not automatically repeated. Failures require `--retry-failed`; a retry is an operational attempt, not another planned repetition. Every current-cohort request, including a retry, retains the 32,000-token ceiling. Earlier exploratory 16,000-token and mixed-budget results are kept in a separately archived study and excluded from current article/resource metrics. The legacy exploratory recovery procedure does not define this cohort.

The pilot permits up to six concurrent case requests, capped at two per provider, with a 900-second transport timeout. Four previously valid Mistral responses at 32,000 tokens were imported after exact frozen-request-hash verification. Imports retain source-attempt provenance and are not reissued. The other 29 case jobs required 30 new API calls, including one same-ceiling Anthropic format retry. Thus the current ledger contains 34 retained API attempts: four reused and 30 new.

`model_resources.csv` is regenerated at phase end and groups resources by model and phase. It reports input/output/total tokens, API duration totals and means, `n_api_calls`, and separate `n_reused_responses`/`n_new_api_calls` counts. Imported responses contribute their original measured usage/time once; newly issued requests contribute their recorded usage/time. The table describes the declared 32,000-token cohort, including its own failed/retried attempts, rather than the cost of earlier discarded exploratory runs.

Resource summaries count actual case API attempts across all recorded current-cohort attempts, including failures and retries. They preserve available request duration, provider token counters and measurement-coverage counts. Unknown duration/token values remain unavailable. API duration is a round trip including network waiting, not model CPU time; sums of parallel request durations are not wall-clock runtime.

Formal agreement compares valid binary compliance/violation answers with the verified trace checker. Non-applicability, uncertainty, unavailable references and failures remain separate. Conditional agreement uses comparable binary answers as its denominator; valid-output and comparable-output coverage use all planned rule assessments. Empty denominators remain unavailable. Formal agreement is not legal accuracy, and formal answers/statistics must not enter the blinded expert package. Report this as a descriptive eleven-case pilot: the 627 rule rows are clustered within those cases and batched model requests. Neither failed output nor legal `undetermined` can be mapped to a negative violation finding.

## Legacy rule mode and cleanup

`assessment_mode: "rule"` retains the earlier root-level `run_manifest.json`, `prepared/`, `requests/`, `llm_assessments.csv`, `comparison_by_pair.csv` and detailed summary layout. Its request count is cases × rules × models × conditions × repetitions. B/C in that mode use supplied `evidence_jsonl`, rather than case-mode local extraction. Existing experiments should retain their original configuration and output directory.

`python run_assessment.py --delete` permanently removes all generated contents of the project-root `outputs` directory, including previous runs and archives. The same flag can precede preparation/execution but cannot be combined with `analyse`. It is not needed for resuming an existing experiment.
